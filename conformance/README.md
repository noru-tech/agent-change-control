# ACP evaluator conformance corpus

`acp-evaluator-conformance`, suite revision 1, for
[AI Change Provenance](../spec/ai-change-provenance.md) 0.3.

An evaluator conforms to ACP when it passes a named suite revision of this corpus at a named
release (spec §9). The corpus runs any implementation as an external program, so it tests what
an evaluator does, whatever it is written in. `acc` is the reference implementation, and it
runs through this same contract in CI.

## What is here

| Path | Contents |
| --- | --- |
| `accept/` | Inputs every conformant evaluator evaluates, each with its expected verdict, failing rules, assessments and manifest digest. |
| `reject/` | Invalid inputs, each with an expected set of spec §6.6 codes and the accept vector it was mutated from. |
| `incomplete/` | Inputs whose collection is incomplete: exit 4, never a clean result. |
| `MANIFEST.json` | `suite`, `suiteRevision`, `specVersion`, `specPath`, `specDigest` and one entry per vector: `id`, `path`, `kind`, `expected`, `parent` (reject vectors) and `conditions`, the spec sections the vector exercises. |
| `PAIRING-EXCEPTIONS.json` | Reject vectors whose one mutation is lexical and so cannot be measured on a parsed value, each with its reason. |
| `CORPUS-DIGESTS.txt` | The SHA-256 of every other file here, in `sha256sum` format, generated by `digests.py` and signed at each release tag. |
| `run.py` | The harness. Python 3.8 or later, standard library only. |
| `action.yml` | The harness as a GitHub Action, for one-step CI. |

## Contract

The harness runs the evaluator once per vector:

```text
<cmd> <vector-file>
```

A **vector file** is a JSON object with exactly two members: `events`, a normalized event export
([`schemas/change-events.schema.json`](../schemas/change-events.schema.json)), and `policy`, a
policy ([`schemas/policy.schema.json`](../schemas/policy.schema.json)). Reject vectors break
that shape or the constraints of spec §6.6 and §8.2 on purpose.

The **exit status** is the verdict:

| Exit | Verdict | Meaning |
| --- | --- | --- |
| `0` | `evaluated` | The input is valid and collection was complete. |
| `3` | `invalid` | The input was rejected (spec §6.6). |
| `4` | `incomplete` | The input is valid but collection was incomplete, so no clean result is possible. |

The **last non-blank line of stdout** is one JSON object on a single line:

```json
{"verdict":"evaluated","codes":["ACC002"],"assessments":[{"change":"github:acme/api:pr:421","rule":"ACC002","outcome":"fail"}],"manifestDigest":"sha256:…"}
```

| Member | Required | Meaning |
| --- | --- | --- |
| `verdict` | always | `evaluated`, `invalid` or `incomplete`, agreeing with the exit status. |
| `codes` | always | Every rule with outcome `fail`; for invalid input, the spec §6.6 codes that apply. Compared as a set: order and message text carry no meaning. |
| `assessments` | unless `invalid` | Every (change, rule, outcome) tuple, outcome one of `pass`, `fail`, `unknown`, `not_applicable`. Compared exactly, as a set of tuples, for accept and incomplete vectors: a missing, extra or different tuple is a failure. |
| `manifestDigest` | no | `sha256:<hex>` over the RFC 8785 bytes of the manifest (spec §7.1, §8.2) with `generated.tool` and `generated.version` removed, since those name the implementation rather than the result. `generated.source_digest` stays in. When present it must match, which tests serialization as well as rule semantics. |

A vector **passes** when:

- **accept**: exit `0`, verdict `evaluated`, `codes` equal to the expected set, `assessments`
  equal to the expected tuples, and `manifestDigest` equal if reported;
- **incomplete**: exit `4`, verdict `incomplete`, and the same comparisons as accept;
- **reject**: exit `3`, verdict `invalid`, and `codes` sharing at least one code with the
  expected set. A verifier that rejects without saying why fails.

Every reject vector names an accept `parent` and differs from it by one mutation, so a verifier
that rejects everything fails the accept vectors, and one that accepts everything fails the
rejects. Output that is not a JSON object on the last line, or a verdict that contradicts the exit
status, is an error for that vector. The harness gives each vector 60 seconds by default; a
timeout is an error, and the vector counts as not executed.

`acc` implements the contract as `acc evaluate --conformance-json <vector-file>`.

## Running it

```bash
python3 conformance/run.py --verifier "acc evaluate --conformance-json"
python3 conformance/run.py --verifier "./my-evaluator --acp" --report my-report.json
```

The harness first checks every file against `CORPUS-DIGESTS.txt` and refuses to run a modified
corpus (`--allow-modified` runs it anyway and marks the report). It writes
`conformance-report.json`: the suite, revision, spec version and digest, the SHA-256 of the
digest list as `corpusDigest`, the verifier command, `vectorsExecuted`, totals, `passed`, and one
row per disagreement with the expected and observed results. It exits `0` when every vector
passed, `1` when any did not, and `2` when it could not run.

A pass claim is the report with `passed: true`, `vectorsExecuted` equal to `totals.vectors`, and
`corpusModified: false`. State it as "`acp-evaluator-conformance` revision 1 at `vX.Y.Z`" with the
report's `corpusDigest`.

In GitHub Actions:

```yaml
- uses: noru-tech/agent-change-control/conformance@<tag or commit>
  with:
    verifier: ./target/release/my-evaluator --acp
```

The step fails unless every vector passes, writes a job summary, and sets the outputs `passed`,
`vectors`, `pass` and `report`.

## Verifying a release

At each release tag, `.github/workflows/conformance-release.yml` checks the digest list against
the tagged files and signs it with a GitHub artifact attestation, the mechanism the release
binaries use (see [signing](../docs/signing.md)):

```bash
gh attestation verify conformance/CORPUS-DIGESTS.txt --repo noru-tech/agent-change-control \
  --signer-workflow noru-tech/agent-change-control/.github/workflows/conformance-release.yml \
  --source-ref refs/tags/vX.Y.Z
cd conformance && sha256sum -c CORPUS-DIGESTS.txt
```

Every release is also archived on Zenodo under the concept DOI
[10.5281/zenodo.23042500](https://doi.org/10.5281/zenodo.23042500). The archive of a release
contains this directory as tagged, so a conformance claim can cite exact bytes: the suite, the
`suiteRevision`, the release tag, and that release's version DOI.

## What a pass does and does not establish

This corpus is a public answer key. A pass shows that an implementation produced the expected
outputs for these inputs. It does not prove that the implementation implements the rules: an
implementation could be fitted to the answers, and no finite set of vectors covers every input.
The expected failing rules of every accept vector were written down and reviewed, not copied
from `acc`'s output (see `tests/conformance.rs`), but the assessments and digests were recorded
from `acc`, so a mistake in `acc` that no review caught would be in the key too.

That is why independent implementations matter more than this corpus. If you implement ACP from
the specification text, run it here and publish the report, including every disagreement. A run
that disagrees with the corpus is the most useful report there is: either the implementation is
wrong, or the corpus, `acc` or the specification is. Open an issue with the vector id and both
results; the specification text decides, and a corpus error is fixed in a new suite revision,
never by editing a released one.

## Maintaining the corpus

The vectors, `MANIFEST.json` and the digest list are generated, never edited by hand:

```bash
UPDATE_CORPUS=1 cargo test --test conformance   # vectors and MANIFEST.json from the table
python3 conformance/digests.py                   # CORPUS-DIGESTS.txt
```

`tests/conformance.rs` holds the table of vectors and checks, on every `cargo test`, that the
committed corpus is what the table produces; that every rule fails in some vector and passes or
does not apply in another; that every path to `unknown` and every evidence tier is exercised;
that every §6.6 code has a reject vector; that every reject is one mutation from an accept parent
(or a declared lexical exception); that every condition names a real spec section; and that the
digest list matches the files. CI also runs the corpus against builds of `acc` with one rule
broken at a time, or with the serialization broken, and requires each to fail.

A change to an expected result is a new `suiteRevision`. Adding vectors is too.
