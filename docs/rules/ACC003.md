# ACC003: Merged change without independent human approval

**A merged change fails when no human independent of its effective human approved the merged head before merge.**

| | |
| --- | --- |
| Rule ID | `ACC003` |
| Policy key | `merged_without_independent_approval` |
| Default severity | `high` (SARIF level `error`) |
| Fails the default policy (`fail_on: medium`) | yes |
| Specification | [AI Change Provenance §6.2](../../spec/ai-change-provenance.md#62-rules) |
| Conditions and fixtures | [docs/policy.md](../policy.md#exact-deterministic-conditions) |

## Why it matters

This is the change-control test for every merged change, human or agent: an authorized, independent
approval must cover what was actually merged. Approvals that were dismissed, superseded by a
"changes requested", given on an earlier commit, or given after the merge do not count.

## Outcomes

Every change gets exactly one outcome for this rule; only `fail` produces a finding. The
reason strings are the exact `reason` text `acc` writes into the assessment.

| Outcome | When | Reason text |
| --- | --- | --- |
| `fail` | The change is merged, the effective human is known, reviews are complete, and no qualifying approval exists. | "No qualifying independent human approval of the current head exists before merge." |
| `pass` | A different human's latest decision at or before merge approves the current head (or, under `agent_review`, a qualifying agent approval does). | "A different human approved the current head before merge, with no later withdrawal recorded."<br>"An agent independent of the effective author on every required dimension approved the current head before merge, as permitted by policy." |
| `unknown` | The effective human is unknown or below the evidence minimum, review collection is incomplete, or an agent approval is unknown on a required dimension. | "Effective human author is unknown; independence cannot be established."<br>"Effective human author's evidence is below the policy minimum; independence cannot be established."<br>"Review collection is incomplete; missing independent approval cannot be established."<br>"An agent approved the current head, but its independence from the effective author is unknown on a required dimension." |
| `not_applicable` | The change is not merged. | "Change has not been merged." |

## Controls

[docs/control-mapping.md](../control-mapping.md) names ACC003 under SOC 2 CC8.1 ("independent
approval before merge"). The same document maps the change-control evidence as a whole, which
ACC003 is part of, to:

- SOC 2 (2017 TSC) CC8.1: changes are authorized, designed, tested, approved and implemented under change-management procedures
- ISO/IEC 27001:2022 Annex A: A.8.32 Change management; A.5.3 Segregation of duties; A.8.25 Secure development life cycle
- PCI DSS v4.0.1 6.5.1: changes follow change-control procedures including approval by authorized parties
- NIST SP 800-53 Rev. 5: CM-3 Configuration change control; CM-5 Access restrictions for change; AC-5 Separation of duties
- NIST SP 800-218 (SSDF): PS.1 Protect code from unauthorized access and tampering; PW.7 Review and/or analyze human-readable code
- SLSA Source track (draft): reviewed changes on protected branches

Typical control response, from the same document: Missed review or an approval that did not cover the merged head.

The mapping is a guide for control owners, not a compliance claim.

## Failing example

Fixture: [`tests/fixtures/dismissed-approval/`](../../tests/fixtures/dismissed-approval/events.json). `bob` approved, but the approval was dismissed before merge.

```console
$ acc evaluate tests/fixtures/dismissed-approval/events.json --format json \
    | jq -c '.assessments[] | select(.rule_id == "ACC003") | {status, reason}'
{"status":"fail","reason":"No qualifying independent human approval of the current head exists before merge."}
```

The manifest carries one `ACC003` finding (`acc-0f9627abec6db796`, severity `high`) whose `explanation` is the reason above and whose `provenance` cites the API records it rests on.

## Passing example

Fixture: [`tests/fixtures/human-clean/`](../../tests/fixtures/human-clean/events.json). `bob`'s approval of the head stands at merge time.

```console
$ acc evaluate tests/fixtures/human-clean/events.json --format json \
    | jq -c '.assessments[] | select(.rule_id == "ACC003") | {status, reason}'
{"status":"pass","reason":"A different human approved the current head before merge, with no later withdrawal recorded."}
```

## How to fix

- The change is already merged: perform a retrospective review and record a disposition, or
  revert.
- Prevent recurrence with branch protection that dismisses stale approvals and requires an
  approval on the latest commit, and with the [GitHub Action](../github-action.md) as a required
  check.

## Recording a disposition

A finding is never deleted. To record a human decision about it, edit only the finding's
`disposition` in the manifest (`accepted`, `remediated` or `false_positive`, with `owner`,
`decided_at`, `rationale`, and `remediated_at` or an optional `expires_at`), then run
`acc check MANIFEST --as-of YYYY-MM-DD`. The date is required because the machine clock is never
read. A disposition suppresses the finding from the threshold decision on that date and leaves the
finding, its evidence and the summary intact; when `--policy` makes `acc check` re-evaluate the
manifest, dispositions carry over by finding ID. Exact rules: [policy and dispositions](../policy.md#recording-exceptions).

```json
{
  "status": "accepted",
  "owner": "security@example.com",
  "decided_at": "2026-09-01",
  "expires_at": "2026-09-30",
  "rationale": "Emergency patch; retrospective review completed.",
  "remediated_at": null
}
```

To change how the rule is enforced rather than record a one-off decision, set its severity or
disable it under `rules.merged_without_independent_approval` in a [policy](../policy.md). Disabling a rule removes its
finding and assessment; it never alters the recorded facts.
