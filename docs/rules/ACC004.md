# ACC004: Merged without required checks

**A merged change fails when a required check did not pass on its head or merge commit before
the merge.**

| | |
| --- | --- |
| Rule ID | `ACC004` |
| Policy key | `merged_without_required_checks` |
| Default severity | `high` (SARIF level `error`) |
| Enabled by default | no: turn it on in a [policy](../policy.md#required-checks) |
| Specification | [AI Change Provenance §6.2](../../spec/ai-change-provenance.md#62-rules), collection in [§4.1](../../spec/ai-change-provenance.md#41-checks) |
| Conditions and fixtures | [docs/policy.md](../policy.md#exact-deterministic-conditions) |

## Why it matters

An independent approval says a person looked at the change. It does not say the tests ran. A
change that merged while a required check was failing, or before it ever ran, was approved on an
untested commit, and branch protection that should have stopped it either was not configured,
was configured differently at the time, or was bypassed.

## What counts

The required checks are the policy's `checks.required` and, with `checks.from_forge: true` (the
default), the checks the repository's rules require on the branch the change merged into: active
rulesets, repository and organization, and classic branch protection.

A required check passes when, on the head commit or on the merge commit, its **latest result
completed at or before the merge** is `success`, `neutral` or `skipped`. When several results
complete at the same instant, every one must pass. The merge commit counts because a merge queue
runs checks on the commit it merges, not on the head. A required check with no result at all
fails. Check runs are matched by name and commit statuses by context, as the forge does.

## Outcomes

Every change gets exactly one outcome for this rule when it is enabled; only `fail` produces a
finding. The reason strings are the exact `reason` text `acc` writes into the assessment.

| Outcome | When | Reason text |
| --- | --- | --- |
| `fail` | The change is merged, check collection is complete, and a required check did not pass, or never ran, on the head or merge commit before the merge. | "Required checks did not pass on the head or merge commit before merge: NAME (did not pass), NAME (no run)." |
| `pass` | Every required check passed on the head or merge commit before the merge. | "Every required check passed on the head or merge commit before merge." |
| `unknown` | Check facts were not collected, or a listing was incomplete; or, under `from_forge`, the forge's required checks could not all be read and every known required check passed. | "Check data was not collected for this change."<br>"Check collection is incomplete."<br>"The forge's required checks could not all be read; required checks cannot be established." |
| `not_applicable` | The change is not merged, or no check is required. | "Change has not been merged."<br>"No checks are required for this change." |

**Incomplete data never passes.** When a policy enables ACC004, a merged change whose check facts
are missing or partial makes the collection incomplete: `acc scan`, `acc check` and
`acc evaluate` exit `4`, as for an incomplete review history. A policy that leaves ACC004 off is
not affected.

## Collecting the facts

`acc scan` and `acc pr` collect check runs, commit statuses and the required checks whenever the
policy enables ACC004; `acc export --checks` collects them for a later `evaluate`. The token needs
to read checks and statuses. In a GitHub Actions workflow:

```yaml
permissions:
  contents: read
  pull-requests: read
  checks: read
  statuses: read
```

Rulesets are read from `GET /repos/{owner}/{repo}/rules/branches/{branch}`, which needs only
read access. Classic branch protection is read from the branch's `protection` summary; when the
token cannot see it, the required set is incomplete and ACC004 is `unknown`. If that is your
case, list the checks in `checks.required` and set `from_forge: false`.

## Limits

- **The required set is today's, not the one at merge time.** GitHub keeps no record of the rules
  in force at an earlier moment. A check added to the rules after a change merged is required of
  that change too; read old windows with that in mind, or list the checks explicitly.
- **Checks posted only to the test merge commit cannot be read after the merge.** Some external
  CI reports a status on the pull request's test merge commit, whose SHA GitHub discards once the
  change merges. Such a check reads as `no run`. Record a disposition, or report the status on the
  head commit.
- **More than 1000 check suites on one commit** are truncated by GitHub; `acc` cannot detect that
  truncation.

## Controls

The evidence maps to testing before change implementation:

- SOC 2 (2017 TSC) CC8.1: changes are authorized, designed, tested, approved and implemented
  under change-management procedures
- ISO/IEC 27001:2022 Annex A: A.8.29 Security testing in development and acceptance; A.8.32
  Change management
- PCI DSS v4.0.1 6.5.1: changes are tested before deployment
- NIST SP 800-53 Rev. 5: CM-3 Configuration change control (test, validate and document changes)

The mapping is a guide for control owners, not a compliance claim.

## Failing example

Fixture: [`tests/fixtures/checks-failed/`](../../tests/fixtures/checks-failed/events.json).
`ci / test` failed on the head before the merge and passed only after it.

```console
$ acc evaluate tests/fixtures/checks-failed/events.json \
    --policy tests/fixtures/checks-failed/policy.yml --format json \
    | jq -c '.assessments[] | select(.rule_id == "ACC004") | {status, reason}'
{"status":"fail","reason":"Required checks did not pass on the head or merge commit before merge: ci / test (did not pass)."}
```

The finding's actors include the merger, and its `provenance` cites the rules and branch records
the required set was read from.

## Passing example

Fixture: [`tests/fixtures/checks-passed/`](../../tests/fixtures/checks-passed/events.json).
`ci / test` failed, was fixed, and passed on the head before the merge.

```console
$ acc evaluate tests/fixtures/checks-passed/events.json \
    --policy tests/fixtures/checks-passed/policy.yml --format json \
    | jq -c '.assessments[] | select(.rule_id == "ACC004") | {status, reason}'
{"status":"pass","reason":"Every required check passed on the head or merge commit before merge."}
```

## How to fix

- The change is already merged: run the checks on the merged commit, review the result, and
  record a disposition, or revert.
- Prevent recurrence with required status checks in a ruleset or branch protection, and do not
  grant bypass to the roles that merge.

## Recording a disposition

A finding is never deleted. To record a human decision about it, edit only the finding's
`disposition` in the manifest (`accepted`, `remediated` or `false_positive`, with `owner`,
`decided_at`, `rationale`, and `remediated_at` or an optional `expires_at`), then run
`acc check MANIFEST --as-of YYYY-MM-DD`. Exact rules: [policy and dispositions](../policy.md#recording-exceptions).

To change how the rule is enforced rather than record a one-off decision, set its severity or
disable it under `rules.merged_without_required_checks` in a [policy](../policy.md). Disabling a
rule removes its finding and assessment; it never alters the recorded facts.
