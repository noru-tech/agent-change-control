# ACC001: Agent change without independent human approval

**An agent-written change fails when no human independent of the agent's operator approved its current head before merge.**

| | |
| --- | --- |
| Rule ID | `ACC001` |
| Policy key | `agent_change_without_independent_human` |
| Default severity | `high` (SARIF level `error`) |
| Fails the default policy (`fail_on: medium`) | yes |
| Specification | [AI Change Provenance §6.2](../../spec/ai-change-provenance.md#62-rules) |
| Conditions and fixtures | [docs/policy.md](../policy.md#exact-deterministic-conditions) |

## Why it matters

When an agent opens a pull request under its own account and the engineer who directed it
approves, the forge shows two different actors, but only one human judged the change. ACC001
asks the question the four-eyes principle actually poses for an agent-written change: did a human
other than the agent's operator approve the commit that was merged? Agent authorship alone is
never a finding; a declared agent change with an independent approval passes.

## Outcomes

Every change gets exactly one outcome for this rule; only `fail` produces a finding. The
reason strings are the exact `reason` text `acc` writes into the assessment.

| Outcome | When | Reason text |
| --- | --- | --- |
| `fail` | The effective author is an agent, its operator is known, review collection is complete, and no qualifying approval exists. | "No qualifying independent human approval of the current head exists before merge." |
| `pass` | A different human's latest decision at or before merge approves the current head (or, under `agent_review`, a qualifying agent approval does). | "A different human approved the current head before merge, with no later withdrawal recorded."<br>"An agent independent of the effective author on every required dimension approved the current head before merge, as permitted by policy." |
| `unknown` | The operator is unknown or below `minimum_authorship_evidence`, review collection is incomplete, or an agent approval is unknown on a required dimension. | "Effective human author is unknown; independence cannot be established."<br>"Effective human author's evidence is below the policy minimum; independence cannot be established."<br>"Review collection is incomplete; missing independent approval cannot be established."<br>"An agent approved the current head, but its independence from the effective author is unknown on a required dimension." |
| `not_applicable` | The effective author is not an agent. | "Effective author is not an agent." |

## Controls

[docs/control-mapping.md](../control-mapping.md) names ACC001 under SOC 2 CC8.1 ("agent changes
with independent review"). The same document maps the change-control evidence as a whole, which
ACC001 is part of, to:

- SOC 2 (2017 TSC) CC8.1: changes are authorized, designed, tested, approved and implemented under change-management procedures
- ISO/IEC 27001:2022 Annex A: A.8.32 Change management; A.5.3 Segregation of duties; A.8.25 Secure development life cycle
- PCI DSS v4.0.1 6.5.1: changes follow change-control procedures including approval by authorized parties
- NIST SP 800-53 Rev. 5: CM-3 Configuration change control; CM-5 Access restrictions for change; AC-5 Separation of duties
- NIST SP 800-218 (SSDF): PS.1 Protect code from unauthorized access and tampering; PW.7 Review and/or analyze human-readable code
- ISO/IEC 42001:2023: human oversight of AI systems and accountability for AI-assisted outputs
- SLSA Source track (draft): reviewed changes on protected branches

Typical control response, from the same document: Treat as a missed four-eyes review; retrospective review and a disposition, or a required status check going forward.

The mapping is a guide for control owners, not a compliance claim.

## Failing example

Fixture: [`tests/fixtures/claude-operator-self-approved/`](../../tests/fixtures/claude-operator-self-approved/events.json). Claude Code wrote the change, `alice` operated it, and the only approval is `alice`'s own.

```console
$ acc evaluate tests/fixtures/claude-operator-self-approved/events.json --format json \
    | jq -c '.assessments[] | select(.rule_id == "ACC001") | {status, reason}'
{"status":"fail","reason":"No qualifying independent human approval of the current head exists before merge."}
```

The manifest carries one `ACC001` finding (`acc-76345141bc169388`, severity `high`) whose `explanation` is the reason above and whose `provenance` cites the API records it rests on.

## Passing example

Fixture: [`tests/fixtures/claude-clean/`](../../tests/fixtures/claude-clean/events.json). The same change, approved on its head by `bob`, who did not operate the agent.

```console
$ acc evaluate tests/fixtures/claude-clean/events.json --format json \
    | jq -c '.assessments[] | select(.rule_id == "ACC001") | {status, reason}'
{"status":"pass","reason":"A different human approved the current head before merge, with no later withdrawal recorded."}
```

## How to fix

- Have a human other than the operator review and approve the current head, then re-run. A new
  commit after the approval invalidates it: approvals bind to the head SHA.
- If the operator is recorded wrongly, fix the `agent-change-control` block in the pull request
  description (see [authorship](../agent-authorship.md)); `acc` never guesses an operator.
- Going forward, gate merges with the [GitHub Action](../github-action.md) as a required check.

## Recording a disposition

A finding is never deleted. To record a human decision about it, edit only the finding's
`disposition` in the manifest (`accepted`, `remediated` or `false_positive`, with `owner`,
`decided_at`, `rationale`, and `remediated_at` or an optional `expires_at`), then run
`acc check MANIFEST --as-of YYYY-MM-DD`. The date is required because the machine clock is never
read. A disposition suppresses the finding from the threshold decision on that date and leaves the
finding, its evidence and the summary intact; when `--policy` makes `acc check` re-evaluate the
manifest, dispositions carry over by finding ID. Exact rules: [policy and dispositions](../policy.md#recording-exceptions).

```json
{
  "status": "accepted",
  "owner": "security@example.com",
  "decided_at": "2026-09-01",
  "expires_at": "2026-09-30",
  "rationale": "Emergency patch; retrospective review completed.",
  "remediated_at": null
}
```

To change how the rule is enforced rather than record a one-off decision, set its severity or
disable it under `rules.agent_change_without_independent_human` in a [policy](../policy.md). Disabling a rule removes its
finding and assessment; it never alters the recorded facts.
