# ACV004: Inconsistent timeline or identities

**An input is rejected when its timeline or identifiers are inconsistent.**

| | |
| --- | --- |
| Code | `ACV004` |
| Kind | Validation code: the input is rejected |
| Exit code | [3](../exit-codes.md#3-invalid-input-or-manifest) |
| Specification | [AI Change Provenance §6.6](../../spec/ai-change-provenance.md#66-validation) |
| Raised by | `src/normalize/mod.rs` (every `ACV004 …` message) |

## Why it matters

Independence is decided by order: the latest decision per reviewer, before merge, on the current
head. A timeline that cannot be ordered, or identifiers that collide, would make that order
arbitrary, and inventing a chronology would invent a verdict. The cases are: a reversed window, or
a window whose completeness and reason disagree; a merge before opening, a merge time without a
merger or the reverse, a merge commit on an unmerged change; a review before opening; duplicate
change, review or commit identifiers; two decisions by one reviewer at one instant that disagree;
a change whose repository differs from the export's; an invalid timestamp.

## Controls

No control mapping is documented for validation codes: they guard the integrity of the input, not
a change-control objective. Their effect on evidence is that a rejected export never yields a
clean result. See [control mapping](../control-mapping.md) for how the findings map.

## Failing example

Input: [`tests/fixtures/conflicting-simultaneous/events.json`](../../tests/fixtures/conflicting-simultaneous/events.json). `bob` approves and requests changes on the same head at the same instant. Reject vectors in [`conformance/reject/`](../../conformance/reject/) cover a [reversed window](../../conformance/reject/human-clean--window-reversed.json), a [review before opening](../../conformance/reject/human-clean--review-before-opening.json), a [duplicate review ID](../../conformance/reject/comment-after-approval--duplicate-review-id.json) and a [merge commit on an unmerged change](../../conformance/reject/open-pr--merge-commit-unmerged.json).

```console
$ acc evaluate tests/fixtures/conflicting-simultaneous/events.json > /dev/null
error: ACV004 ambiguous simultaneous reviews (see https://github.com/noru-tech/agent-change-control/blob/main/docs/rules/ACV004.md)
$ echo $?
3
```

## Passing example

Input: [`tests/fixtures/human-clean/events.json`](../../tests/fixtures/human-clean/events.json). One decision per reviewer and instant, all after opening and before merge.

```console
$ acc evaluate tests/fixtures/human-clean/events.json --format table > /dev/null
$ echo $?
0
```

## How to fix

The message names the inconsistency. Re-collect if the export was edited or truncated; if two
decisions really share a timestamp, the forge data cannot be ordered and the producer must resolve
it rather than `acc` guessing.

## Disposition

A validation code is not a finding and cannot carry a disposition. The input is rejected
outright: `acc` writes no manifest, findings or assessments for it and exits 3, because an
evaluator must not reach a verdict on facts that do not hold together
([spec §6.6](../../spec/ai-change-provenance.md#66-validation)). Fix the input, or the producer
that wrote it, and run again. If an export written by `acc export` or `acc scan` fails
validation, please [report it](https://github.com/noru-tech/agent-change-control/issues/new/choose).
