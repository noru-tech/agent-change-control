# ACV009: Nesting too deep

**An input is rejected when it is not I-JSON as ACP constrains it: nesting depth is at most 128, counting the outermost container as depth 1; input is rejected at the first container past the bound, without parsing further.**

| | |
| --- | --- |
| Code | `ACV009` |
| Kind | Validation code: the input is rejected |
| Exit code | [3](../exit-codes.md#3-invalid-input-or-manifest) |
| Specification | [AI Change Provenance §6.6](../../spec/ai-change-provenance.md#66-validation), [§8.2](../../spec/ai-change-provenance.md#82-serialization) |
| Raised by | `src/canonical/ijson.rs` |

## Why it matters

Unbounded nesting is a denial-of-service vector for recursive parsers, and no ACP document needs anywhere near 128 levels. The check runs while parsing, before the schema or any rule, on every JSON or YAML input `acc` reads (events, manifests, policies, attestations). Messages give a byte offset, never input text.

## Controls

No control mapping is documented for validation codes: they guard the integrity of the input, not
a change-control objective. Their effect on evidence is that a rejected export never yields a
clean result. See [control mapping](../control-mapping.md) for how the findings map.

## Failing example

Input: [`tests/fixtures/ijson/depth-129.json`](../../tests/fixtures/ijson/depth-129.json). A document nested 129 levels deep.

```console
$ acc evaluate tests/fixtures/ijson/depth-129.json > /dev/null
error: ACV009 nesting deeper than 128 at byte 488 (see https://github.com/noru-tech/agent-change-control/blob/main/docs/rules/ACV009.md)
$ echo $?
3
```

## Passing example

Input: [`tests/fixtures/human-clean/events.json`](../../tests/fixtures/human-clean/events.json). A well-formed export.

```console
$ acc evaluate tests/fixtures/human-clean/events.json --format table > /dev/null
$ echo $?
0
```

## How to fix

Fix the producer that wrote the value; ACP documents never need it. The byte offset in the message points at the offending token. If the document came from `acc` itself, report it as a bug.

## Disposition

A validation code is not a finding and cannot carry a disposition. The input is rejected
outright: `acc` writes no manifest, findings or assessments for it and exits 3, because an
evaluator must not reach a verdict on facts that do not hold together
([spec §6.6](../../spec/ai-change-provenance.md#66-validation)). Fix the input, or the producer
that wrote it, and run again. If an export written by `acc export` or `acc scan` fails
validation, please [report it](https://github.com/noru-tech/agent-change-control/issues/new/choose).
