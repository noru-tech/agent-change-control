# ACC007: Agent approval recorded (observation)

**ACC007 records, as an observation, every change whose current head an agent approved.**

| | |
| --- | --- |
| Rule ID | `ACC007` |
| Policy key | `agent_approval_recorded` |
| Default severity | `info` (SARIF level `note`) |
| Fails the default policy (`fail_on: medium`) | no |
| Specification | [AI Change Provenance §6.2](../../spec/ai-change-provenance.md#62-rules) |
| Conditions and fixtures | [docs/policy.md](../policy.md#exact-deterministic-conditions) |

## Why it matters

An agent's approval never counts as a human's. ACC007 is not a violation: it makes the population
of agent-approved changes visible, so a control owner can sample it and see how far agent review
has spread. It evaluates under every policy.

## Outcomes

Every change gets exactly one outcome for this rule; only `fail` produces a finding. The
reason strings are the exact `reason` text `acc` writes into the assessment.

| Outcome | When | Reason text |
| --- | --- | --- |
| `fail` | An agent's latest decision at or before merge approves the current head (an `info` observation). | "An agent approved the current head." |
| `pass` | An agent reviewed the current head without approving it. | "An agent reviewed the current head without approving it." |
| `unknown` | Never. | (none) |
| `not_applicable` | No agent reviewed the current head. | "No agent reviewed the current head." |

## Controls

[docs/control-mapping.md](../control-mapping.md) does not map ACC007 to a control objective. Its
reading table describes the expected response: "None by itself; the population of agent-approved
changes for sampling." No control mapping is documented for this rule.

The mapping is a guide for control owners, not a compliance claim.

Fixture: [`tests/fixtures/agent-review-declared/`](../../tests/fixtures/agent-review-declared/events.json). An OpenAI review agent (`github:review-bot`) approved Claude Code's change. (The fixture also fails ACC001 and ACC003, because an agent approval does not replace a human one.)

```console
$ acc evaluate tests/fixtures/agent-review-declared/events.json --format json \
    | jq -c '.assessments[] | select(.rule_id == "ACC007") | {status, reason}'
{"status":"fail","reason":"An agent approved the current head."}
```

The manifest carries one `ACC007` finding (`acc-a398bb6a8dde09f8`, severity `info`) whose `explanation` is the reason above and whose `provenance` cites the API records it rests on.

## How to fix

Nothing to fix: ACC007 is `info`, below every useful `fail_on`, and never fails the default
policy on its own. If you want an agent approval to satisfy independence, that is the opt-in
`agent_review` policy, checked by [ACC009](ACC009.md) and [ACC010](ACC010.md). To stop recording
it, disable the rule in a policy (`agent_approval_recorded: {enabled: false, severity: info}`).

## Recording a disposition

A finding is never deleted. To record a human decision about it, edit only the finding's
`disposition` in the manifest (`accepted`, `remediated` or `false_positive`, with `owner`,
`decided_at`, `rationale`, and `remediated_at` or an optional `expires_at`), then run
`acc check MANIFEST --as-of YYYY-MM-DD`. The date is required because the machine clock is never
read. A disposition suppresses the finding from the threshold decision on that date and leaves the
finding, its evidence and the summary intact; when `--policy` makes `acc check` re-evaluate the
manifest, dispositions carry over by finding ID. Exact rules: [policy and dispositions](../policy.md#recording-exceptions).

```json
{
  "status": "accepted",
  "owner": "security@example.com",
  "decided_at": "2026-09-01",
  "expires_at": "2026-09-30",
  "rationale": "Emergency patch; retrospective review completed.",
  "remediated_at": null
}
```

To change how the rule is enforced rather than record a one-off decision, set its severity or
disable it under `rules.agent_approval_recorded` in a [policy](../policy.md). Disabling a rule removes its
finding and assessment; it never alters the recorded facts.
