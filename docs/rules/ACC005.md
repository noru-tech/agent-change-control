# ACC005: Merged with protection bypass

**A merged change fails when the forge recorded that the push landing it bypassed a ruleset.**

| | |
| --- | --- |
| Rule ID | `ACC005` |
| Policy key | `merged_with_protection_bypass` |
| Default severity | `high` (SARIF level `error`) |
| Enabled by default | no: turn it on in a [policy](../policy.md#protection-bypass) |
| Specification | [AI Change Provenance §6.2](../../spec/ai-change-provenance.md#62-rules), collection in [§4.2](../../spec/ai-change-provenance.md#42-protection-bypass) |
| Conditions and fixtures | [docs/policy.md](../policy.md#exact-deterministic-conditions) |

## Why it matters

Branch protection is the control that makes approvals and checks mandatory rather than
advisory. A merge that bypassed it did not have to meet either, whatever the other rules say
about the change. A bypass may be legitimate, for an emergency fix, but it is an exception, and
an exception needs an owner and a reason.

## What counts

GitHub records a **rule suite** each time rulesets evaluate a push: its result is `pass`, `fail`,
or `bypass` when the rules failed and an actor with bypass permission pushed anyway. `acc`
records the rule suites whose push landed the change's merge commit.

- A `bypass` evaluation fails the rule, even when the rest of the record is incomplete.
- Every evaluation `pass`: the rule passes.
- A `fail` evaluation whose push still landed: `unknown`, because the rules that failed may have
  been in evaluate mode rather than enforced, and the record does not say which.
- **No evaluation recorded: `unknown`, never `pass`.** No ruleset may apply to the branch, or the
  pushing actor may be exempt from it. GitHub records nothing for an exempt actor, and an
  administrator's override of classic branch protection is visible only in the Enterprise
  organization audit log, which `acc` does not read. An empty record is not evidence that nothing
  was bypassed.

## Outcomes

Every change gets exactly one outcome for this rule when it is enabled; only `fail` produces a
finding. The reason strings are the exact `reason` text `acc` writes into the assessment.

| Outcome | When | Reason text |
| --- | --- | --- |
| `fail` | The change is merged and a recorded ruleset evaluation of its merge is `bypass`. | "A ruleset evaluation of the merge records a bypass: the rules failed and the push landed anyway." |
| `pass` | Every recorded evaluation of the merge passed. | "Every ruleset evaluation of the merge passed." |
| `unknown` | Evaluations were not collected or are incomplete; an evaluation failed but the push landed; or none is recorded. | "Ruleset evaluations were not collected for this change."<br>"Ruleset evaluations for this change could not be read, or are older than the forge's listing reaches."<br>"A ruleset evaluation of the merge failed but the push landed; whether active protection was bypassed cannot be established."<br>"No ruleset evaluation of the merge is recorded; a push by an exempt actor or an override of classic branch protection leaves none, so a bypass cannot be ruled out." |
| `not_applicable` | The change is not merged. | "Change has not been merged." |

**Incomplete data never passes.** When a policy enables ACC005, a merged change whose
evaluations could not be read, or whose merge is older than the listing reaches, makes the
collection incomplete: `acc scan`, `acc check` and `acc evaluate` exit `4`.

## Collecting the facts

`acc scan` and `acc pr` collect rule suites whenever the policy enables ACC005;
`acc export --bypass` collects them for a later `evaluate`. They come from
`GET /repos/{owner}/{repo}/rulesets/rule-suites`, which needs **repository administration read
access**. The `GITHUB_TOKEN` of a GitHub Actions workflow cannot be granted it; use a GitHub App
installation token or a fine-grained token with *Administration: read*, and keep it to the job
that runs `acc`.

GitHub lists rule suites for at most the past month. `acc` treats anything merged more than 28
days before collection as out of reach, so collect each window soon after it closes, for example
from a scheduled workflow.

## Limits

- **Exempt actors and classic-protection overrides leave no record** that this API exposes; see
  above. Prefer rulesets with `bypass_mode: always` (recorded) over exemptions, and do not grant
  bypass to the roles that merge.
- **One month of history.** Older merges cannot be judged after the fact.
- **Merge queues.** A merge queue lands the commit it tested; if that commit is not the merge
  commit GitHub reports for the pull request, no evaluation matches and the result is `unknown`.

## Controls

- SOC 2 (2017 TSC) CC8.1: changes are authorized and implemented under change-management
  procedures; CC6.1: logical access controls protect against unauthorized changes
- ISO/IEC 27001:2022 Annex A: A.8.32 Change management; A.8.4 Access to source code
- NIST SP 800-53 Rev. 5: CM-5 Access restrictions for change

The mapping is a guide for control owners, not a compliance claim.

## Failing example

Fixture: [`tests/fixtures/bypass-recorded/`](../../tests/fixtures/bypass-recorded/events.json).
The push that landed the merge commit is recorded with result `bypass`.

```console
$ acc evaluate tests/fixtures/bypass-recorded/events.json \
    --policy tests/fixtures/bypass-recorded/policy.yml --format json \
    | jq -c '.assessments[] | select(.rule_id == "ACC005") | {status, reason}'
{"status":"fail","reason":"A ruleset evaluation of the merge records a bypass: the rules failed and the push landed anyway."}
```

The finding's actors include the merger, and its `provenance` cites the rule suite.

## Passing example

Fixture: [`tests/fixtures/bypass-passed/`](../../tests/fixtures/bypass-passed/events.json). The
rulesets evaluated the push that landed the merge commit and it passed.

```console
$ acc evaluate tests/fixtures/bypass-passed/events.json \
    --policy tests/fixtures/bypass-passed/policy.yml --format json \
    | jq -c '.assessments[] | select(.rule_id == "ACC005") | {status, reason}'
{"status":"pass","reason":"Every ruleset evaluation of the merge passed."}
```

## How to fix

- The change is already merged: review it as you would an unreviewed change, confirm the
  required checks pass on it, and record a disposition naming who bypassed and why.
- Prevent recurrence by narrowing who may bypass and requiring that a bypass goes through a pull
  request.

## Recording a disposition

A finding is never deleted. To record a human decision about it, edit only the finding's
`disposition` in the manifest (`accepted`, `remediated` or `false_positive`, with `owner`,
`decided_at`, `rationale`, and `remediated_at` or an optional `expires_at`), then run
`acc check MANIFEST --as-of YYYY-MM-DD`. Exact rules: [policy and dispositions](../policy.md#recording-exceptions).

To change how the rule is enforced rather than record a one-off decision, set its severity or
disable it under `rules.merged_with_protection_bypass` in a [policy](../policy.md). Disabling a
rule removes its finding and assessment; it never alters the recorded facts.
