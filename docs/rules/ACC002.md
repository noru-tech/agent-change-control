# ACC002: Effective human author or operator approved own change

**A change fails when its effective human (the human author, or the agent's operator) approved it at any point.**

| | |
| --- | --- |
| Rule ID | `ACC002` |
| Policy key | `approver_is_author` |
| Default severity | `high` (SARIF level `error`) |
| Fails the default policy (`fail_on: medium`) | yes |
| Specification | [AI Change Provenance §6.2](../../spec/ai-change-provenance.md#62-rules) |
| Conditions and fixtures | [docs/policy.md](../policy.md#exact-deterministic-conditions) |

## Why it matters

Self-approval is the classic segregation-of-duties failure, and coding agents make it easy to
miss: the operator who directed the agent can approve "the agent's" pull request and the forge
records it as someone else's change. ACC002 records the act itself, so a stale self-approval that
no longer counts still shows up.

## Outcomes

Every change gets exactly one outcome for this rule; only `fail` produces a finding. The
reason strings are the exact `reason` text `acc` writes into the assessment.

| Outcome | When | Reason text |
| --- | --- | --- |
| `fail` | Any `approved` review, at any time, is by the effective human. | "The effective human author or agent operator approved this change." |
| `pass` | Review collection is complete and no approval by the effective human exists. | "No self-approval was observed in complete review data." |
| `unknown` | The effective human is unknown or below the evidence minimum, or reviews are incomplete and no self-approval was seen. | "Effective human author is unknown; independence cannot be established."<br>"Effective human author's evidence is below the policy minimum; independence cannot be established."<br>"Review collection is incomplete." |
| `not_applicable` | Never. | (none) |

## Controls

[docs/control-mapping.md](../control-mapping.md) names ACC002 under SOC 2 CC8.1 ("self-approval").
The same document maps the change-control evidence as a whole, which ACC002 is part of, to:

- SOC 2 (2017 TSC) CC8.1: changes are authorized, designed, tested, approved and implemented under change-management procedures
- ISO/IEC 27001:2022 Annex A: A.8.32 Change management; A.5.3 Segregation of duties; A.8.25 Secure development life cycle
- PCI DSS v4.0.1 6.5.1: changes follow change-control procedures including approval by authorized parties
- NIST SP 800-53 Rev. 5: CM-3 Configuration change control; CM-5 Access restrictions for change; AC-5 Separation of duties
- NIST SP 800-218 (SSDF): PS.1 Protect code from unauthorized access and tampering; PW.7 Review and/or analyze human-readable code

Typical control response, from the same document: Self-approval; the same response as for any author-approved change.

The mapping is a guide for control owners, not a compliance claim.

## Failing example

Fixture: [`tests/fixtures/human-self-approved/`](../../tests/fixtures/human-self-approved/events.json). `alice` opened the change and approved it herself.

```console
$ acc evaluate tests/fixtures/human-self-approved/events.json --format json \
    | jq -c '.assessments[] | select(.rule_id == "ACC002") | {status, reason}'
{"status":"fail","reason":"The effective human author or agent operator approved this change."}
```

The manifest carries one `ACC002` finding (`acc-bd288824f2c3dee5`, severity `high`) whose `explanation` is the reason above and whose `provenance` cites the API records it rests on.

## Passing example

Fixture: [`tests/fixtures/human-clean/`](../../tests/fixtures/human-clean/events.json). `alice` opened the change and `bob` approved it.

```console
$ acc evaluate tests/fixtures/human-clean/events.json --format json \
    | jq -c '.assessments[] | select(.rule_id == "ACC002") | {status, reason}'
{"status":"pass","reason":"No self-approval was observed in complete review data."}
```

## How to fix

- A self-approval cannot be undone; the finding records that it happened. Get an independent
  approval of the current head (which clears ACC001 and ACC003) and record a disposition for
  ACC002 if your process accepts the retrospective review.
- GitHub already stops a pull request's opener from approving it, but not the human who operates
  an agent account from approving that agent's pull request. Require an approval from someone
  other than the operator (for example through CODEOWNERS), and gate merges on `acc`.

## Recording a disposition

A finding is never deleted. To record a human decision about it, edit only the finding's
`disposition` in the manifest (`accepted`, `remediated` or `false_positive`, with `owner`,
`decided_at`, `rationale`, and `remediated_at` or an optional `expires_at`), then run
`acc check MANIFEST --as-of YYYY-MM-DD`. The date is required because the machine clock is never
read. A disposition suppresses the finding from the threshold decision on that date and leaves the
finding, its evidence and the summary intact; when `--policy` makes `acc check` re-evaluate the
manifest, dispositions carry over by finding ID. Exact rules: [policy and dispositions](../policy.md#recording-exceptions).

```json
{
  "status": "accepted",
  "owner": "security@example.com",
  "decided_at": "2026-09-01",
  "expires_at": "2026-09-30",
  "rationale": "Emergency patch; retrospective review completed.",
  "remediated_at": null
}
```

To change how the rule is enforced rather than record a one-off decision, set its severity or
disable it under `rules.approver_is_author` in a [policy](../policy.md). Disabling a rule removes its
finding and assessment; it never alters the recorded facts.
