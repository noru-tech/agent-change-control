# ACC013: Deployed without passing change

**A production deployment fails when it shipped a commit no merged change landed, or one a failing change landed.**

| | |
| --- | --- |
| Rule ID | `ACC013` |
| Policy key | `deployed_without_passing_change` |
| Default severity | `high` (SARIF level `error`) |
| Enabled by default | no |
| Subject | a deployment (`FORGE:REPOSITORY:deployment:ID`), not a change |
| Specification | [AI Change Provenance §6.2](../../spec/ai-change-provenance.md#62-rules), collection in [§4.6](../../spec/ai-change-provenance.md#46-deployments) |
| Conditions and fixtures | [docs/policy.md](../policy.md#exact-deterministic-conditions) |

## Why it matters

[`acc verify`](../verify.md) is the gate before a deployment: it refuses a range of commits that
are not each landed by a passing change. This rule is the same question asked afterwards, of every
deployment that reached production, including the ones that never went through the gate.

## What counts

For each successful deployment to a production environment (the policy's
`deployments.environments`, or those the forge marks as production) in the deployment window, every
commit it shipped: the first-parent commits after the environment's previous successful
deployment, up to and including the one deployed. Each must be the merge commit of a merged change
that passes the policy, judged by the same evaluation: no assessment of the change at or above
`fail_on` is `fail`.

Dispositions are applied later, by `acc check`, and do not reach into this rule: a deployment of a
change whose finding was accepted keeps its own finding until it has its own disposition.

## Outcomes

| Outcome | When | Reason text |
| --- | --- | --- |
| `fail` | A shipped commit dated inside the merge window was landed by no change, or by a change that fails. | "The deployment to ENV shipped commits not covered by a passing change; landed by no change: …; landed by a change that fails: …." |
| `pass` | Every shipped commit was landed by a passing change, and the history is complete. | "Every commit the deployment shipped was landed by a change that passes the policy." |
| `unknown` | No commit fails, and the history is incomplete or has no earlier deployment to bound it, a commit is dated before the merge window, or a change that landed one is unknown. | "The commits the deployment shipped could not all be read, or no earlier deployment bounds them."<br>"Commits merged before the collection window cannot be judged: …; collect changes from earlier."<br>"Commits landed by a change whose verdict is unknown: …." |

**Incomplete data never passes.** With ACC013 enabled, a missing deployment record, a listing
read in part, or a deployment whose history is incomplete makes the collection incomplete:
`acc scan`, `acc check` and `acc evaluate` exit `4`.

## Collecting the facts

`acc scan` collects deployments whenever the policy enables ACC013; `acc export --deployments` (the
forge's production environments) or `--environment NAME` collects them for a later `evaluate`.
`--deploy-since DATE` starts the deployment window later than the merge window, so the changes a
deployment shipped were merged inside it. On GitHub the facts come from the deployments and
deployment statuses APIs (`deployments: read`) and the compare API for the history. On GitLab this
version records the deployments as unreadable, and the rule is `unknown`. `acc pr` judges one
change and leaves this rule to `acc scan`.

## Controls

- SOC 2 (2017 TSC) CC8.1: changes are authorized, tested and approved before implementation
- ISO/IEC 27001:2022 Annex A: A.8.32 Change management; A.8.31 Separation of development, test and production environments
- NIST SP 800-53 Rev. 5: CM-3 Configuration change control; CM-14 Signed components

The mapping is a guide for control owners, not a compliance claim.

## How to fix

- Review what the deployment shipped, and record a disposition on its finding.
- Prevent recurrence: gate deployments with [`acc verify`](../verify.md), so a commit no passing
  change landed never reaches production.

## Recording a disposition

A finding is never deleted. To record a human decision about it, edit only the finding's
`disposition` in the manifest (`accepted`, `remediated` or `false_positive`, with `owner`,
`decided_at`, `rationale`, and `remediated_at` or an optional `expires_at`), then run
`acc check MANIFEST --as-of YYYY-MM-DD`. Exact rules: [policy and dispositions](../policy.md#recording-exceptions).
