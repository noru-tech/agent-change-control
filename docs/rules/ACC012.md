# ACC012: Unaccounted branch update

**A protected branch fails when it was force-pushed, deleted, or pushed to a commit no merged change landed.**

| | |
| --- | --- |
| Rule ID | `ACC012` |
| Policy key | `unaccounted_branch_update` |
| Default severity | `high` (SARIF level `error`) |
| Enabled by default | no |
| Subject | a branch (`FORGE:REPOSITORY:branch:NAME`), not a change |
| Specification | [AI Change Provenance §6.2](../../spec/ai-change-provenance.md#62-rules), collection in [§4.5](../../spec/ai-change-provenance.md#45-branch-updates) |
| Conditions and fixtures | [docs/policy.md](../policy.md#exact-deterministic-conditions) |

## Why it matters

Every other rule judges a pull request. A direct push to `main`, or a force push that rewrites it,
is not a pull request, so no change rule ever sees it: the code it shipped was never reviewed, and
the history a later review would read may have been replaced. This rule makes those updates a
population of their own.

## What counts

For each protected branch (the policy's `branches.protected`, or the repository's default branch),
every update recorded in the window. An update is unaccounted for when it is:

- a force push;
- a deletion of the branch;
- a push whose resulting commit is not the merge commit of any merged change in the window.

A merge of a pull request, a merge-queue merge and the branch's creation are accounted for.

## Outcomes

| Outcome | When | Reason text |
| --- | --- | --- |
| `fail` | At least one update is unaccounted for. One finding per update. | "N update(s) of BRANCH no change accounts for: KINDS." |
| `pass` | Every update in a complete record is accounted for. | "Every recorded update of the branch landed a change." |
| `unknown` | The record is incomplete and no unaccounted update was seen. | "The branch's updates in the window could not be read in full." |

Each finding names its update in `change_id` (`github:acme/api:branch:main#900`), and its
explanation says what happened: "Force push to main by github:alice at TIME, from
BEFORE to AFTER.", "Direct push to main by … which no change landed.", or "Deletion of main by …".

**Incomplete data never passes.** With ACC012 enabled, a missing or incomplete branch record makes
the collection incomplete: `acc scan`, `acc check` and `acc evaluate` exit `4`.

## Collecting the facts

`acc scan` collects the branches whenever the policy enables ACC012; `acc export --branches` (the
default branch) or `--branch NAME` collects them for a later `evaluate`. On GitHub they come from
the repository activity record (`GET /repos/{owner}/{repo}/activity`), which reaches a year back
from collection: an older window is incomplete. GitLab's push events do not say whether a push was
forced or landed a merge request, so on GitLab the record is incomplete and the rule is `unknown`.
`acc pr` judges one change and leaves this rule to `acc scan`.

## Controls

- SOC 2 (2017 TSC) CC8.1: changes are authorized, tested and approved before implementation
- ISO/IEC 27001:2022 Annex A: A.8.32 Change management; A.8.4 Access to source code
- NIST SP 800-53 Rev. 5: CM-3 Configuration change control; CM-5 Access restrictions for change

The mapping is a guide for control owners, not a compliance claim.

Fixture: [`tests/fixtures/branch-accounted/`](../../tests/fixtures/branch-accounted/events.json).
The only update in the window is PR 421's merge.

## How to fix

- Find out what the update shipped, review it, and record a disposition on its finding.
- Prevent recurrence: require pull requests for the branch, block force pushes and deletions, and
  do not grant bypass to the roles that push.

## Recording a disposition

A finding is never deleted. To record a human decision about it, edit only the finding's
`disposition` in the manifest (`accepted`, `remediated` or `false_positive`, with `owner`,
`decided_at`, `rationale`, and `remediated_at` or an optional `expires_at`), then run
`acc check MANIFEST --as-of YYYY-MM-DD`. Exact rules: [policy and dispositions](../policy.md#recording-exceptions).
