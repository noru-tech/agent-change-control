# ACC008: Same-vendor write and review

**An agent-written change fails when it has approvals but no human approval, and every approving agent comes from the author agent's vendor.**

| | |
| --- | --- |
| Rule ID | `ACC008` |
| Policy key | `same_vendor_write_and_review` |
| Default severity | `high` (SARIF level `error`) |
| Fails the default policy (`fail_on: medium`) | yes |
| Specification | [AI Change Provenance §6.2](../../spec/ai-change-provenance.md#62-rules) |
| Conditions and fixtures | [docs/policy.md](../policy.md#exact-deterministic-conditions) |

## Why it matters

When the only approvals of an agent's change come from agents built by the same vendor, one model
family checked its own work. ACC008 makes that visible under every policy, whether or not agent
review is allowed to satisfy independence. The vendor comparison is deliberately coarse: it
answers that one question and nothing finer.

## Outcomes

Every change gets exactly one outcome for this rule; only `fail` produces a finding. The
reason strings are the exact `reason` text `acc` writes into the assessment.

| Outcome | When | Reason text |
| --- | --- | --- |
| `fail` | The effective author is an agent, at least one approval of the head exists, no human approved it, and every approving agent has the author agent's vendor. | "Every approval of the current head is by an agent of the author agent's vendor." |
| `pass` | An agent of another vendor approved the current head. | "An agent of another vendor approved the current head." |
| `unknown` | The author agent's or an approving agent's vendor is null (unregistered). | "The author agent's or an approving agent's vendor is unknown; same-vendor review cannot be established." |
| `not_applicable` | The effective author is not an agent, a human approved the head, or nothing approved it. | "Effective author is not an agent."<br>"A human approved the current head."<br>"No approval of the current head exists." |

## Controls

[docs/control-mapping.md](../control-mapping.md) does not map ACC008 to a specific control
objective. Its reading table describes it as "one model checking its own work; treat as a missed
independent review", which is the separation-of-duties concern mapped there for the evidence as a
whole:

- ISO/IEC 27001:2022 Annex A: A.8.32 Change management; A.5.3 Segregation of duties; A.8.25 Secure development life cycle
- NIST SP 800-53 Rev. 5: CM-3 Configuration change control; CM-5 Access restrictions for change; AC-5 Separation of duties

Typical control response, from the same document: One model checking its own work; treat as a missed independent review.

The mapping is a guide for control owners, not a compliance claim.

## Failing example

Fixture: [`tests/fixtures/agent-review-same-vendor/`](../../tests/fixtures/agent-review-same-vendor/events.json). Claude Code (vendor `anthropic`) wrote the change; the only approval is from a review agent also registered to `anthropic`.

```console
$ acc evaluate tests/fixtures/agent-review-same-vendor/events.json --format json \
    | jq -c '.assessments[] | select(.rule_id == "ACC008") | {status, reason}'
{"status":"fail","reason":"Every approval of the current head is by an agent of the author agent's vendor."}
```

The manifest carries one `ACC008` finding (`acc-6904dd1993972afa`, severity `high`) whose `explanation` is the reason above and whose `provenance` cites the API records it rests on.

## Passing example

Fixture: [`tests/fixtures/agent-review-independent/`](../../tests/fixtures/agent-review-independent/events.json). The approving agent is registered to `openai`. (This fixture is evaluated with its `policy.yml`, which turns on `agent_review`.)

```console
$ acc evaluate tests/fixtures/agent-review-independent/events.json --policy tests/fixtures/agent-review-independent/policy.yml --format json \
    | jq -c '.assessments[] | select(.rule_id == "ACC008") | {status, reason}'
{"status":"pass","reason":"An agent of another vendor approved the current head."}
```

## How to fix

- Have a human, or an agent of a different vendor, approve the current head.
- If a vendor is wrong or missing, register it: `--agent-vendor AGENT=VENDOR` on the collecting
  commands (the built-in registry covers common agents).

## Recording a disposition

A finding is never deleted. To record a human decision about it, edit only the finding's
`disposition` in the manifest (`accepted`, `remediated` or `false_positive`, with `owner`,
`decided_at`, `rationale`, and `remediated_at` or an optional `expires_at`), then run
`acc check MANIFEST --as-of YYYY-MM-DD`. The date is required because the machine clock is never
read. A disposition suppresses the finding from the threshold decision on that date and leaves the
finding, its evidence and the summary intact; when `--policy` makes `acc check` re-evaluate the
manifest, dispositions carry over by finding ID. Exact rules: [policy and dispositions](../policy.md#recording-exceptions).

```json
{
  "status": "accepted",
  "owner": "security@example.com",
  "decided_at": "2026-09-01",
  "expires_at": "2026-09-30",
  "rationale": "Emergency patch; retrospective review completed.",
  "remediated_at": null
}
```

To change how the rule is enforced rather than record a one-off decision, set its severity or
disable it under `rules.same_vendor_write_and_review` in a [policy](../policy.md). Disabling a rule removes its
finding and assessment; it never alters the recorded facts.
